ACT 2 • DYNAMIC MATRIX STORY: PART 1

Dynamic Matrix Story: The Original Problem & Impact

Why naive CI testing collapses when your monorepo scales.

The Original Issue

  • Monorepo grew to hundreds of interconnected local packages.
  • Every affected package was tested sequentially in a single job. Zero parallelism.
  • Some PRs took 2h 15m to test and analyze (398 packages).
  • Failures surfaced only at the end: ~1h 4m just to learn a PR was red.

The Business & Dev Impact

  • Developers context-switched while waiting on red/green signals.
  • Engineers batched giant PRs to avoid waiting twice (multiplying merge conflicts).
  • Every fail → fix → re-push cycle cost another 1–2 hours of waiting.
  • PRs missed the release cut while the pipeline was still running.
ACT 2 • DYNAMIC MATRIX STORY: PART 2 Started as my proposal • Feb 2025

The Clever Solution: Diff-Aware Dynamic Matrices

Compute the exact blast radius at runtime, isolate heavy modules, and fan out.

.github/workflows/pr.yaml Melos + jq + fromJson 
PACKAGES=$(melos list --diff=origin/${{ github.base_ref }}...HEAD \
  --include-dependents --json)
# Isolate memory-heavy packages into dedicated batches
if [ "$HAS_UNICLIENT_NAVIGATION" = "true" ]; then
  RESOURCE_HEAVY_BATCHES+=('["uniclient_navigation"]')
fi
# Chunk remaining packages into batches of 50
PACKAGE_BATCHES=$(echo "$REMAINING" | jq -c \
  --argjson sz 50 '[range(0; length; $sz) as $i | .[$i:$i+$sz]]')
---
test-batch:
  strategy:
    fail-fast: false
    matrix:
      batch_index: ${{ fromJson(needs.matrix-preparation.outputs.test_batch_numbers) }}

INTERACTIVE CHALLENGE #1 • 30-SEC DEBUG

Spot the $600/Day Pipeline Leak (And How We Fixed It)

leaky-pr-matrix.yaml 22 Parallel Matrix Nodes 
name: PR Matrix Validation
jobs:
  test:
    strategy:
      matrix:
        package: ${{ fromJson(needs.setup.outputs.packages) }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with:
          flutter-version: '3.24.0'
      - run: flutter test
The Leak: Every node boots a clean VM and downloads/extracts the ~1 GB Flutter SDK 22 times per PR (~$600/day in wasted compute).

30-Second Crime Scene Clues

  • 1.strategy.matrix fans out across up to 22 parallel runners.
  • 2.Look at runs-on: ubuntu-latest paired with subosito/flutter-action@v2.
fixed-pr-matrix.yaml SDK Baked In + Drift Guard 
jobs:
  resolve-image:  # newest ECR tag, no hand-bumps
    outputs: { image: ... }
  test:
    needs: [setup, resolve-image]
    strategy: { matrix: <same fan-out> }
    runs-on: [self-hosted, flutter]
    container:
      image: ${{ needs.resolve-image.outputs.image }}
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/init
        # baked SDK == requested? skip download
        # drifted? fall back + alert Slack
      - run: flutter test
The Solution: Bake the SDK into a self-hosted runner image, resolve the newest image tag at runtime, and guard against drift. If the image falls behind the repo's Flutter version, every job silently re-downloads the SDK. That's what cost us ~$600/day.
ACT 2 • ACTIONABLE PLAYBOOK

Four Universal CI Velocity Multipliers

1. Pre-Warmed Runner Images & Analyzer Cache

Bake the Flutter SDK into runner images (and alert when it drifts); warm_analyzer_cache.yaml rebuilds the Dart analyzer cache on every push to main so PRs restore warm cache instantly.

2. Auto-Cancel Stale Runs

Set concurrency: cancel-in-progress: true on PR workflows so pushing a quick fix immediately kills obsolete runs.

3. Sparse Checkouts for Governance

Dependency graph jobs checkout only **/pubspec.yaml and the validator script—sub-second clones instead of pulling gigabytes of assets.

4. Selective Coverage Collection

Collect coverage metrics only for packages with modified .dart or pubspec.yaml files.

ACT 5 • LOOKING AHEAD — BAZEL

The Next Chapter: Exploring the Bazel Horizon

The Limitation of Diff-Based Gates

  • Diff gates are fantastic at stopping NEW debt in changed packages.
  • However, they cannot easily clean up OLD legacy debt sitting quietly on main in untouched files.
  • Running full-graph validation on every PR becomes too slow without fine-grained caching.

Why Teams Explore Bazel

  • True Monorepo Scale: Orchestrates Dart, Flutter, iOS, and Android native tooling under one language-agnostic rule set.
  • Hermetic & Content-Addressed: Builds are pure. Same inputs = exactly the same outputs.
  • Remote Caching: Developers and CI machines share AWS S3 caches. If CI built it, the developer’s local laptop downloads it instantly (e.g., fully cached iOS simulator builds in 1.3 seconds).
ACT 5 • LOOKING AHEAD — BAZEL

How Bazel Works: Fingerprint, Cache, Reuse

Hermetic builds

Every target gets a fingerprint

Bazel splits the repo into small targets and hashes everything that goes into each one. No network, no machine-specific paths: same inputs, same output, on any machine.

• key = sha256(source + deps + toolchain + flags)
• 1,119 BUILD.bazel files generated by Gazelle
Shared remote cache

CI builds once, everyone reuses it

CI uploads each output to S3, keyed by its fingerprint. Every CI runner and every laptop reads from the same cache.

• CI: read-write
• Fork PRs: read-only (--config=ci-ro)
Only the blast radius rebuilds

Change one file in cards

The fingerprint of cards changes, and so does every target that depends on it. Everything else is a cache hit: downloaded, not rebuilt.

• 2 rebuilt • 3 from cache
• Fully cached iOS simulator build: 1.3s
